# i18n Rules

## Overview

This project **already uses** `nestjs-i18n` throughout — services, controllers, DTO validators,
guards, the validation pipe, and the response handler. Every user-facing string (response message,
exception message, validation message, email copy) goes through i18n. Never hardcode an English
literal in a controller, service, DTO, or repository.

`I18nModule` (`libs/common/src/i18n/i18n.module.ts`, exported from `@common`) configures it:

- **Catalogs** live at `libs/common/src/i18n/lang/<lang>/<namespace>.json`. Languages: `en`
  (fallback) and `id`, with `en-*` → `en` and `id-*` → `id` fallbacks. Namespaces:
  `message.json`, `validation.json`, `email.json`.
- **Resolvers** (in order): `?lang` / `?locale` query, `x-lang` / `x-custom-lang` header,
  `Accept-Language`.
- **`disableMiddleware: true` is deliberate.** Under the Fastify adapter the i18n middleware's async
  context does not propagate to the route handler, which would leave `I18nContext.current()`
  undefined and silently fall back to `en`. With the middleware off, the global
  `I18nLanguageInterceptor` registered by `I18nModule.forRoot` resolves the language and wraps the
  handler. **Do not re-enable the middleware.**
- `watch` is on outside production, so catalog edits hot-reload in `make dev`.

## Catalog structure

`message.json` is grouped by domain: `common`, `app`, `auth`, `user`, `role`, `permission`. Keys are
addressed with the namespace prefix and a dotted path — `message.common.success`,
`message.user.not_found`, `message.auth.invalid_credentials`. Interpolation uses `{name}`
placeholders (`"User with ID {id} not found"`).

`validation.json` is keyed by **constraint name in UPPER_SNAKE** — `NOT_EMPTY`, `IS_STRING`,
`IS_EMAIL`, `IS_STRONG_PASSWORD`, `IS_ENUM`, `IS_ARRAY`, `IS_UUID` — not by field. Each entry
interpolates `{property}`, which `CustomValidationPipe` injects from the failing field name, so one
entry serves every DTO. Add a new key only when you introduce a class-validator constraint that has
none yet, and name it after the decorator.

`email.json` holds mail copy, grouped per template (`verify_email`, `forgot_password`).

When you add a domain module, add its group to **`message.json` in both `en` and `id`**,
variable-identical, *before* writing code that references the keys. Do not create new top-level
namespace files unless a whole new catalog is warranted — extend `message.json`.

## Service layer — inject `I18nService`

Never pass a raw string to `NotFoundException`, `UnprocessableEntityException`, etc.

```ts
import { I18nService } from "nestjs-i18n";

@Injectable()
export class UsersService {
	constructor(private readonly i18n: I18nService) {}

	/* Returns a single user, or throws when the id does not resolve. */
	async findOne(id: string): Promise<UserDetail> {
		const data = await UserRepository().findOne(id);
		if (!data) {
			throw new NotFoundException(
				this.i18n.t("message.user.not_found", { args: { id } }),
			);
		}
		return data;
	}
}
```

## Controller layer — inject `I18nService`

Every message passed to `ResponseHandler.success(status, message, data)` is an i18n lookup, never a
literal:

```ts
return res
	.status(200)
	.send(
		ResponseHandler.success(200, this.i18n.t("message.user.found_success"), data),
	);
```

## DTO layer — `i18nValidationMessage`

Every class-validator decorator carries a message built with `i18nValidationMessage(...)` from
`nestjs-i18n`, keyed into `validation.json` by constraint name:

```ts
import { i18nValidationMessage } from "nestjs-i18n";

@IsString({ message: i18nValidationMessage("validation.IS_STRING") })
@IsNotEmpty({ message: i18nValidationMessage("validation.NOT_EMPTY") })
@IsEmail({}, { message: i18nValidationMessage("validation.IS_EMAIL") })
@ApiProperty({ example: "johndoe@example.com", format: "email" })
email: string;
```

A decorator without a `message` is a bug: it ships class-validator's own English string, untranslated
and off-format. See `dto.md`.

## Guards, pipes, response handler, repositories — `I18nContext.current()`

These are not resolved through normal request DI, so they use the static accessor, and the
`?? "fallback"` is **mandatory** — `I18nContext.current()` returns `undefined` outside a request
(bootstrap, queue processors, some tests). Repository factory functions use it too: they are plain
functions and cannot receive `I18nService` by constructor injection.

```ts
import { I18nContext } from "nestjs-i18n";

throw new BadRequestException(
	I18nContext.current()?.t("message.common.invalid_sort_field") ?? "Invalid sort field",
);
```

Do not inject `I18nService` into a guard, a pipe, or a repository.

## What NOT to translate

- Log messages passed to `LoggerUtils` — logs are always English.
- Internal developer-facing detail (stack traces, Prisma error codes).
- Keys and field names used in structured error payloads — only the message strings are translated.
